# Case Cortex — architecture reference

A Case Cortex generalises the LLM-native wiki pattern from documentation
to any bounded knowledge-work problem. Three primitive operations —
**Ingest** (source → pages), **Query** (question → answer from pages),
**Lint** (hygiene pass) — are preserved as Workflows 3, 5a, and 6 of
this skill respectively. The core operating rule — *one source touches
many pages* — is what gives Layer 1's `entities/` and `concepts/`
directories their richness; see `ingestion.md`.

Each Cortex carries its own per-case operating manual at `CLAUDE.md`
(case root). This is the schema overlay: the document that tells the
LLM how the wiki is structured for *this* specific case (language
convention, jurisdictional defaults, domain-specific page conventions,
tone bias). The generic skill provides the four-layer shape and the
six workflows; `CLAUDE.md` is the per-case overlay that the LLM and the
user co-evolve over time.

`cortex.yaml` records both the Cortex schema version and the skill
version that created or last migrated the Cortex. `cortex_schema`
describes the on-disk contract; `skill_version` describes the
instructions/templates used to operate it.

## The four-layer model

Every full-mode Cortex has the same four layers. They differ in
**volatility**, **ownership**, and **regenerability**.

### Layer 1 — Canonical facts

Five kinds of files live here:

- **Spine files** (`overview.md`, `synthesis.md`, `index.md`) — the
  meta-layer that turns a Cortex from a flat folder of pages into a
  navigable knowledge base. `overview.md` is the narrative entry point
  ("what is this case, why does it exist, where do you start reading");
  `synthesis.md` is the opinion-bearing current best thinking
  ("direction, open risks, parameter calibrations, design patterns
  chosen and rejected"); `index.md` is the curated catalog of every
  page grouped by topical cluster. Without these, entity and concept
  pages drift from any shared frame and the Cortex becomes a searchable
  mess rather than a reasoned position. Spine files are updated on
  every Ingest (see `ingestion.md`).
- **Skeleton files** (`identity.md`, `scope.md`, `context.md`) — short,
  index-like Layer 1 anchors that orient any reader. They list and
  link, they don't deeply describe.
- **Entity pages** (`entities/{slug}.md`) — one rich page per named
  real-world thing with identity that *acts* in the case: people,
  organisations, teams, legal entities, products, systems, projects,
  regulators, jurisdictions. Each carries identity facts, a description,
  a role-in-case section, relationships, and a footprint showing the
  trail the entity has left. Entity pages are generated and updated by
  Ingest. The "can this thing make a phone call?" test routes to
  entities — yes → entity, no but acts in the world → entity, just
  describes a mechanism → concept. (See SKILL.md for the full decision
  tree.)
- **Concept pages** (`concepts/{slug}.md`) — one rich page per
  mechanism, KPI, term-of-art, calculation rule, clause, regime, or
  load-bearing relationship the case touches. *Mechanisms*, not
  *agents*. Generated by Ingest. A substantive case typically has
  20–100 entity + concept pages combined; a sparse case (5–10) is a
  sign of under-ingestion.
- **Source summaries** (`sources/{YYYY-MM-DD}_{slug}.md`) — one rich
  page per ingested source. Narrative-shape: TL;DR, parties involved,
  structural breakdown, key facts, notable quotes, takeaways, plus
  generated-entities and generated-concepts lists. Distinct from
  entity/concept pages (which are fact-shape) and from Layer 3 derived
  artifacts (which are produced *from* the Cortex, not *into* it).
  Source summaries are the bridge between the raw source and the
  fan-out — they make the Cortex auditable.

- **What:** the ground truth of the case. Identity, scope, the set of
  named entities involved with their identity facts and footprints,
  the set of mechanisms/KPIs/terms of art with their definitions and
  trade-offs, stable context (regulatory, sector, historical), the
  reading notes per source, and the spine that ties them together.
- **Volatility:** low for skeleton, medium for entities, concepts, and
  spine (touched on every Ingest), append-only for source summaries.
- **Ownership:** human-owned with agent assistance.
- **Regenerable:** no. This is the source of truth.

### Layer 2 — Working memory

- **What:** the live log of the case. Decisions and their reasoning,
  meeting notes, open questions, hypotheses, risks, blockers, internal
  debates. Captures *how the case is being worked*, not just *what is
  true about it*.
- **Volatility:** high. New entries constantly.
- **Ownership:** append-only by convention. Decisions are superseded,
  not rewritten. Benign edits (typos, formatting, frontmatter
  corrections) are allowed in place; substantive edits must be a new
  entry that supersedes the prior one.
- **Regenerable:** no. This is history.

### Layer 3 — Derived artifacts

- **What:** everything generated from Layers 1 and 2. Briefings,
  analyses, models, reports, decks, summaries, recommendations, lint
  reports. Each carries provenance: inputs consulted, generator,
  timestamp.
- **Volatility:** medium. Regenerated on demand when inputs change.
- **Ownership:** agent-generated, human-reviewed.
- **Regenerable:** yes — disposable by design.
- **Retention:** see "Layer 3 retention" below.

### Layer 4 — Pointers

- **What:** links to external systems of record. CRM records, document
  stores, issue trackers, code repos, communication threads, external
  sources.
- **Volatility:** low to medium. URLs and IDs, not content.
- **Ownership:** largely machine-maintained.
- **Regenerable:** partially — machine-populated from connectors if
  available.

## Directory structure (full mode)

```
{case-name}/
  CLAUDE.md                    # per-case operating manual (schema overlay)
  cortex.yaml                  # case metadata
  README.md                    # human-facing orientation
  01-canonical/
    overview.md                # narrative entry: what is this case, why, where to read
    synthesis.md               # opinion-bearing current best thinking
    index.md                   # curated catalog of every page, grouped by cluster
    identity.md                # name, type, purpose, status, success criteria
    scope.md                   # in/out of scope, constraints, assumptions
    context.md                 # regulatory, sector, historical, competitive
    entities/                  # one rich page per named real-world thing with identity
      {slug}.md
    concepts/                  # one rich page per mechanism, KPI, term-of-art
      {slug}.md
    sources/                   # one rich summary per ingested source
      YYYY-MM-DD_{slug}.md
  02-working-memory/
    decisions.md               # append-only decision log
    open-questions.md          # live questions, marked resolved when answered
    log/
      YYYY-MM-DD-{slug}.md     # dated entries for meetings, events, updates
  03-derived/
    {artifact-kind}/
      YYYY-MM-DD-{slug}.md     # briefings, analyses, reports, lint-reports
    _archive/                  # superseded artifacts kept for reference (see retention)
  04-pointers/
    systems.yaml               # links to CRM, DMS, issue trackers, repos
    external.yaml              # public sources, filings, external URLs
```

## Directory structure (minimal mode)

```
{case-name}/
  CLAUDE.md                    # per-case operating manual
  cortex.yaml                  # case metadata
  README.md                    # human-facing orientation
  notes.md                     # single growing notes file
```

Minimal mode is for cases that have not yet earned the full structure.
The skill watches for migration triggers (notes.md > ~500 lines, the
user starts asking questions the flat structure can't answer, multiple
sources need ingesting) and offers to migrate to full mode. Migration
is mechanical and described in `references/workflows/1-initialize.md`.

Domain templates vary the *content* of Layer 1 skeleton files but not
the structure. Entity pages and concept pages each have the same shape
across every domain. `CLAUDE.md` is generated from
`templates/claude-md-template.md` and customised per case as
conventions emerge.

## Layer 3 retention

Layer 3 artifacts are regenerable by design, but the user often wants
the prior version preserved for reference (a briefing that was actually
delivered to a client; a report that was already cited externally;
prior lint runs as a longitudinal record of cortex health).

Convention:

- **Active artifacts** live at `03-derived/{kind}/{date}-{slug}.md`.
- **Superseded or stale artifacts** are moved to
  `03-derived/_archive/{kind}/{date}-{slug}.md` when a new version is
  generated. The newest version takes the un-archived path.
- **Lint reports** keep the most recent two or three runs at the active
  path; older ones move to `_archive/lint/` so longitudinal trend is
  preserved without crowding the active directory.
- **Archive is not deletion.** The user may explicitly delete
  `_archive/` contents at any time; the skill does not delete archive
  contents on its own.

`index.md` lists active Layer 3 artifacts under their kind. Archived
artifacts are reachable via `_archive/` directly; they do not need to
appear in the index.

## Provenance and staleness

Layer 3 artifacts carry a frontmatter block listing their inputs. The
input format prefers hashes (computed by the skill) over file mtimes.
There are two accepted hash modes:

- **`material-v1`** — preferred. Hash normalized content with YAML
  frontmatter maintenance fields, `## Change Log` sections, and
  whitespace-only differences removed. Use this when code execution or
  a helper script is available.
- **`raw`** — acceptable fallback. Hash the raw file bytes/content.
  This detects every file change, including Change Log appends and
  whitespace edits, so it can create conservative stale warnings. If
  raw hashes are used, say so in the artifact frontmatter.

Do not claim that raw sha256 hashes avoid false positives from Change
Log or whitespace edits; only `material-v1` has that intent.

Format:

```yaml
inputs:
  - path: 01-canonical/concepts/{slug}.md
    hash: sha256:{first-12-chars-of-content-hash}
    hash_mode: material-v1
  - path: 02-working-memory/decisions.md
    hash: sha256:{first-12-chars-of-content-hash}
    hash_mode: material-v1
```

When the skill regenerates or audits an artifact:

- It re-hashes each input's current content.
- If a `material-v1` hash differs, the artifact is *materially stale*
  — flag and offer to regenerate.
- If a `raw` hash differs, the artifact may be stale — flag as
  conservative raw-hash staleness unless a human confirms the change
  was non-substantive.
- If hashes match, the artifact is current regardless of mtime drift.

When git is available the skill may use commit hashes instead of
content hashes. When neither is available, fall back to date-only
markers (`{path}@{YYYY-MM-DD}`) and tell the user staleness detection
is best-effort under that fallback.

## Confidentiality

Every canonical page and derived artifact carries confidentiality in
frontmatter where applicable. The ordered levels are:

`public < internal < restricted < confidential`.

Derived artifacts inherit the strictest confidentiality of all inputs.
For example, a briefing generated from one `public` source and one
`confidential` entity page must be marked `confidential`.

When the user asks for a public or lower-confidentiality artifact from
higher-confidentiality inputs, do not silently produce it. Either:

1. Ask whether to generate it at the higher confidentiality level.
2. Run a redaction pass that removes or generalizes restricted facts,
   then mark the artifact with both `confidentiality: public` and
   `redaction: applied`.

Lint flags a confidentiality downgrade as a **blocker** when no
redaction is recorded, and as a **warning** ("confirm the redaction is
sufficient") when `redaction: applied` is set with non-empty
`redaction_notes`. A `redaction: applied` artifact with missing or
empty `redaction_notes` is itself a warning.

## Concurrency and Git

The Cortex is deliberately file-based, so humans and agents can work in
the same repository. That makes edit discipline part of the operating
model:

- Read the current file immediately before editing it.
- Prefer narrow edits over broad rewrites, especially in Layer 1.
- One agent should own one workflow slice at a time: for example, one
  source ingest, one derived artifact, or one lint report.
- Preserve append-only history when resolving conflicts. If two
  agents add decisions or log entries, keep both and order them by
  date/time rather than choosing a winner.
- Avoid last-writer-wins on `index.md`, `synthesis.md`, `CLAUDE.md`,
  and `cortex.yaml`; merge both sides deliberately and add a Change
  Log entry where the file has one.
- Before large Ingest or Lint work, check git status. If there are
  unrelated user changes, work around them rather than reverting them.
- If a rebase or merge conflict occurs, resolve in favor of preserving
  more provenance and history. It is better to carry a duplicate note
  that lint can later consolidate than to delete a fact with uncertain
  provenance.

## Design commitments

Any Cortex that breaks one of these is something else. Preserve them.

1. **One per case.** Scope-bounded to a single problem. Cross-case
   knowledge emerges from having many Cortexes with the same shape.
2. **Living, not archival.** Updated continuously. Every meaningful
   event either writes to it or is derivable from it.
3. **Dual-access.** Humans edit directly; agents read and write via the
   same interface. Neither is second-class.
4. **Derivative, not duplicative.** Points to systems of record. Does
   not replace them.
5. **Auditable by construction.** Every derived artifact carries
   provenance. Every Layer 1 fact should ideally cite a pointer.

## Why the layers matter

The separation is not cosmetic — it determines what can be done safely:

- Because Layer 3 is regenerable, it can be **deleted and rebuilt** when
  Layer 1 changes. This is the whole reason stale briefings don't
  accumulate.
- Because Layer 2 is append-only, history is **reconstructible**. You
  can always answer "when did we know this?" and "why did we decide
  that?"
- Because Layer 1 is canonical and reviewed, the agent has a **stable
  observation surface**. It doesn't re-infer the world each session.
- Because Layer 4 is just pointers, the Cortex **stays small** regardless
  of how much source material the case touches.
- Because entity pages and concept pages are independently addressable,
  **a single source can fan out into many pages** that each get
  cross-referenced from elsewhere. This is the "one source touches many
  pages" rule — and it is the reason these pages exist as first-class
  primitives in Layer 1 rather than living inside the skeleton files.
- Because entities and concepts are *separate directories with different
  templates*, the Cortex captures the asymmetry between *things that
  act* (people, firms, systems — which need identity facts, role,
  footprint) and *things that describe how something works*
  (mechanisms, KPIs, terms of art — which need definitions, trade-offs,
  edge cases).
- Because the spine files exist, the Cortex has a **shared frame** that
  ties entity and concept pages into a position. Without `synthesis.md`
  you have facts but no view; without `index.md` you have content but
  no navigation; without `overview.md` you have artifacts but no entry
  point for new readers (human or LLM). The spine is what closes the
  *meta-layer gap*: the failure mode where pages get rich but the
  synthesis layer drifts behind reality.
- Because source summaries exist, every entity and concept page's
  provenance is not just a pointer to a raw file but a navigable
  narrative summary of that source. The fan-out becomes auditable: from
  any source summary you can walk to the pages it produced; from any
  page you can walk back to the source summary.
- Because `CLAUDE.md` exists at the case root, the LLM has a **per-case
  operating manual** in addition to the generic skill. The skill says
  *what shape every Cortex has*; `CLAUDE.md` says *what conventions
  this case has chosen*. Without it, every session starts from the
  generic skill and rediscovers the same conventions.

Losing any of these properties collapses the distinction between a
Cortex and "a folder of files," which is what we started with.

## How agents interact with the Cortex

The mental model is: **the Cortex is the observation slot of the
agent's observe → think → act loop.**

- **Observe:** load relevant Cortex slices into the agent context.
  Rarely do you load everything; typically you load Layer 1 plus the
  slice of Layer 2 relevant to the current task.
- **Think:** the agent reasons over structured, provenance-bearing
  content rather than ad-hoc attachments.
- **Act:** the agent writes back. Layer 2 for decisions and events,
  Layer 3 for derived artifacts, occasionally Layer 1 (review-gated)
  for canonical updates.

Multi-agent setups converge because they all observe the same Cortex.
Single agents stay coherent across sessions because the Cortex *is*
their memory.
